# Project instructions

## Business analysis documents

- Treat attached requirement files as content sources, not as visual templates, unless the user explicitly identifies a file as a template.
- Use a professional BRD structure by default: executive summary; background and objectives; scope; stakeholders and roles; AS-IS/TO-BE processes; business rules; functional and non-functional requirements; data, statuses and integrations; SLA, notifications and metrics; Use Cases; User Stories; traceability; assumptions, dependencies, risks, open questions and next steps.
- Use the `standard_business_brief` design preset for new BRDs unless the user requests another visual style.
- Produce the final deliverable as a visually verified `.docx` unless the user asks for a different format.
- Always include dedicated sections for Use Cases and User Stories, even when the source requirements do not provide them explicitly.
- Each Use Case should include: ID and name, goal, actors, preconditions, trigger, main flow, alternative/exception flows, postconditions, and related business rules or requirements.
- Each User Story should include: ID, role, need, business value, acceptance criteria (prefer Given/When/Then), and traceability to related Use Cases or requirements.
- Separate confirmed facts, assumptions, and open questions. Do not invent missing business facts; record unresolved details as open questions or clearly marked assumptions.
